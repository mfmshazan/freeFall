# Phase 1 implementation plan: evidence and gravity

**Outcome:** A user can read a measured Saffire-I result beside the existing replay, understand why an orbiting cabin is effectively weightless at 400 km, and see a spherical still-air flame with honest model uncertainty. This is an implementation checklist; the work below is pending.

**Codex:** GPT-6.1 Sol at **High** for planning refinements and implementation. The checklist is ready to execute without a separate planning turn. GPT-6.1 Terra at **Medium** is optional for visual review after the build. See the [roadmap](IMPLEMENTATION_ROADMAP.md#phases-and-model-choices) for later phases and the [official Codex model guide](https://learn.chatgpt.com/docs/models) for model availability.

## 1. Add the Saffire-I evidence card

- [ ] Add a small curated JSON asset beside the processed [Saffire-I replay assets](frontend/public/replay/saffire-1/conditions.json). Store the primary link, report run IDs (`1-1`, `1-2`), material (SIBAL cotton/fiberglass fabric), orbital microgravity, nominal duct flow (20 cm/s), flow direction, and measured average flame spread (`1.8 mm/s` concurrent, `1.3 mm/s` opposed). If shown, label the reported lengths (~40 mm concurrent plateau, ~24 mm opposed) as approximate and distinguish length from spread. Record the metric as reported from video analysis and include the report page. [NASA Saffire-I report, p. 21](https://ntrs.nasa.gov/api/citations/20170008805/downloads/20170008805.pdf#page=21)
- [ ] Add the card to [SaffireReplay](frontend/src/replay/SaffireReplay.tsx). Label it **Measured results in the NASA report**. Explain that the opposed pass used the fabric remaining after the concurrent pass; the comparison does not isolate flow direction by itself. The replay is a partial image window for the concurrent run; the opposed value comes from the report, and neither number is an instantaneous cursor reading. Keep the card usable with the prediction API offline, and keep playback working if the card asset is unavailable.
- [ ] Keep the two sources separate: the report gives `40.6 × 94 cm` and `21.7%` starting oxygen (identified as an ISS reading); the [replay metadata](frontend/public/replay/saffire-1/conditions.json) gives `300 × 800 mm` and a separate calibrated-data reading at ignition of about `22.62%`. Do not resolve these differences by averaging, relabeling, or treating the two oxygen values as interchangeable. Avoid showing a merged geometry/atmosphere record until the bases are reconciled. Keep both copies of `psi_master.json` and raw assets untouched; document the new derived asset and source limits in [DATA_INVENTORY.md](DATA_INVENTORY.md).

## 2. Separate field strength and effective gravity

- [ ] In [CabinBuilder](frontend/src/components/CabinBuilder.tsx), rename **Gravity** to **Effective cabin gravity**. Keep sending `gravity_g` as the effective acceleration used by the model. Clarify that ISS is nominal free fall; the Moon and Mars buttons refer to supported surface habitats, not orbit. Treat their cabin atmospheres as examples rather than mission specifications.
- [ ] Add a frontend Earth-field calculator in an explicitly labeled **Earth orbit** explainer. Use `field_g = (6371 / (6371 + altitude_km)) ** 2` with a typical display range of `0–2,000 km`, default `400 km`, and units in km. Label 0 km as the surface reference for the field, not an orbital scenario. Show field and effective gravity side by side at the orbital example. Keep altitude out of `CabinInputs` and `/api/predict`; changing it leaves the prediction payload and effective cabin input unchanged. If a user manually adjusts effective gravity, make the custom input distinguishable from the nominal orbital example. [NASA microgravity explanation](https://www.nasa.gov/centers-and-facilities/glenn/what-is-microgravity/) · [NASA surface gravity reference](https://ntrs.nasa.gov/citations/20210024855)
- [ ] In [backend prediction assembly](backend/main.py), apply the physical still-air dimensions when `gravity_g == 0` and `airflow_cm_s == 0`. Use the same physical diameter for length and width and return `aspect_ratio_LD == 1.0`; the GP's independently predicted dimensions currently disagree with that ratio. Leave other geometry behavior to the later model work. Confirm the [offline model](frontend/src/physics/flameModel.ts) uses the same boundary. In [FlameCanvas](frontend/src/components/FlameCanvas.tsx), render the same circular body at that input once the state settles. Preserve the standoff gap, deterministic animation, and no buoyant flicker; the uncertainty halo represents model spread and need not describe a physical flame boundary. Read the [physics spec](skills/01-flame-physics-rules.md) and [canvas spec](skills/02-canvas-animation-spec.md) before edits and bring their contracts into line with any changes.

## 3. Fix claims that can mislead in the first demo

- [ ] In [backend/main.py](backend/main.py) and [offline localService.ts](frontend/src/physics/localService.ts), describe prediction coverage as **No comparable measured outcome used by this model**. Avoid claims that the program knows no partial-gravity measurements exist anywhere; say the current model lacks comparable data. Keep the API and fallback response compatible. In [App](frontend/src/App.tsx) and the [evidence panel](frontend/src/components/EvidencePanel.tsx), identify any seed still surfaced as a synthetic example; label `real_psi` plus `physics_estimate` as **Sourced conditions · estimated outcomes**. Do not show a seed as the closest NASA reference or present its link as a verified run citation. Comprehensive evidence ranking is Phase 2.
- [ ] In the [trust gauge](frontend/src/components/TrustGauge.tsx) and canvas, replace **High confidence**, the numeric trust framing, **95%** coverage claims, and displayed fixed safety multipliers with visible model uncertainty and evidence status. Keep the halo and a range/spread readout. If numbers are shown, label the backend spread as model-based and the offline spread as heuristic; neither is a calibrated interval. Keep internal fields only as needed for compatibility and stop using them to imply a safety decision or to color unsupported cases as validated.
- [ ] Label the canvas palette and soot/heat proxies as illustrative. Remove the **High-O₂ Gas Leak (CFI-G)** claim from the presets and prevent the current heuristic regime from being presented as a confirmed cool flame or an instrument requirement. In the [playbook](frontend/src/components/PlaybookPanel.tsx) and its backend/fallback outputs, replace blanket detector, ventilation, and suppression directions with short, sourced research notes or omit them until sourced. Phase 3 owns the classifier and evidence-led treatment of appearance. [NASA cool flame observations](https://www.nasa.gov/missions/station/cool-flames-created-during-a-first-for-international-space-station-research/)

## Verification before handoff

| Check | Pass condition |
| --- | --- |
| Earth field | `0 km → 1.000 g`; `400 km → 0.885 g` to three decimals. Dragging altitude with the orbital preset keeps the effective input and API body at `0 g`. |
| Surface presets | Earth `1 g`, Moon about `0.165 g` (the existing `0.166 g` preset is an approximation), Mars `0.38 g`. None inherits Earth's altitude calculation. |
| Still-air sphere | The endpoint and the offline path both return identical length/width within each prediction and exact `L/D = 1.0` at zero effective gravity and flow. The settled canvas body is circular with no buoyant flicker. A gravity or airflow change still stretches an applicable flame. |
| Saffire-I | The two reported rates, units, nominal flow, and reused-specimen note agree with the report. Scrubbing still aligns recorded frames and telemetry; the results card remains static. It works when the API is down. |
| Provenance and claims | A seed result cannot read as measured or high confidence; a Saffire legacy estimate cannot read as a measured target. No calibrated `95%`, recommended multiplier, detector guarantee, or prescribed fire-response sequence appears. |
| Data and build | Validate the new JSON and source links and check the two master datasets still match. Run `npm run build` from `frontend/`; run the existing backend suite with `python -m unittest discover -s backend -p 'test_*.py'` from the root using the backend environment. Add a focused boundary regression, since existing mining tests do not cover prediction geometry. Verify the UI with and without the API; report any check that could not run. |

**Out of scope:** changing the model's training data; calibrating uncertainty; a flow-direction or specimen-geometry prediction model; gravity from vehicle dynamics or rotation; new download tooling; and calibrated color. Phase 1 is complete when the comparison is traceable, the gravity behavior passes, and the model limits are visible in both modes.
